API 버전을 올릴 때마다 릴리스 노트를 읽고 수정 파일을 찾는 개발자라면, ChatGPT·Claude·Gemini에 **이전 문서와 새 문서를 함께 넣고 차이표를 먼저 만드는 방식**이 유리하다. 작은 SDK 변경은 무료 계정으로 시험할 수 있다. 다만 AI가 만든 코드만 복사해 배포하는 경우, 보안·호환성·회귀 테스트가 필요한 운영 시스템에는 이 방법을 그대로 적용하면 안 된다.

그림에서 볼 것은 코드 생성이 아니라 `변경 문서 → 영향 범위 → 수정 후보 → 검증 명령 → 사람 승인`의 흐름이다.

## 어떤 결과물을 요구해야 하나

“마이그레이션해줘”라고 하면 모델은 예시 코드를 길게 쓸 가능성이 높다. 실제로 필요한 결과물은 아래 표처럼 추적 가능한 작업표다.

| 항목 | AI에게 맡길 일 | 사람이 확인할 일 |
|---|---|---|
| 변경점 | 추가·삭제·이름 변경을 문서 근거와 함께 추출 | 문서의 버전과 적용일 |
| 영향 범위 | 호출부, 설정키, 테스트 파일 후보 제시 | 저장소 검색 결과와 실제 의존성 |
| 수정안 | 전후 코드 조각과 가정 정리 | 타입·예외·권한 처리 |
| 검증 | 빌드·테스트·스모크 테스트 명령 초안 | CI 환경에서의 실제 통과 여부 |

## 복사해서 쓰는 프롬프트

두 버전의 공식 마이그레이션 문서와 관련 코드 일부를 올린 뒤 아래 프롬프트를 붙인다.

```text
너는 [언어/SDK] 유지보수 담당자다. 첨부한 이전 문서와 새 문서, 코드 조각만 근거로 마이그레이션 검수표를 만들어라.

1. 변경 내용을 [변경 유형, 문서 페이지/절, 근거 문장] 표로 정리한다.
2. 저장소에서 확인해야 할 검색어와 예상 영향 파일을 적는다.
3. 수정 전/후 코드 예시는 필요한 경우에만 쓰고, 문서에 없는 부분은 '확인 필요'로 표시한다.
4. 각 항목에 위험도(낮음/중간/높음), 검증 명령, 완료 조건을 붙인다.
5. 기존 API와 새 API가 동시에 동작한다고 가정하지 마라. 추측한 호환성은 별도 목록으로 분리하라.
```

출력 받은 뒤 `영향 파일`이 실제로 존재하는지 `rg`, `검증 명령`이 프로젝트의 패키지 관리자와 맞는지 확인한다. AI가 제시한 행 번호나 함수명이 틀릴 수 있으므로, 수정 전에 브랜치를 만들고 작은 변경 하나씩 테스트하는 편이 안전하다.

## 무료와 유료의 경계

확인일은 2026년 11월 3일이다. ChatGPT는 문서 업로드와 비교를 지원하지만 무료·유료 모두 파일 업로드와 데이터 분석에 별도 사용 제한이 있다([OpenAI 파일 업로드 안내](https://help.openai.com/en/articles/8555545-uploading-files-and-audio-to-chatgpt)). Claude는 PDF·DOCX·CSV·XLSX 등을 지원하며 채팅 파일은 파일당 30MB, 최대 20개라고 안내한다([Anthropic 문서 업로드 안내](https://support.anthropic.com/en/articles/8241126-what-kinds-of-documents-can-i-upload-to-claude-ai)). Gemini도 문서·코드 파일을 올릴 수 있고 일반 파일은 100MB, 한 프롬프트 최대 10개라는 조건을 안내한다([Google Gemini 파일 분석 안내](https://support.google.com/gemini/answer/14903178?hl=en-mp)). 계정·지역·워크스페이스에 따라 달라질 수 있으니 숫자보다 실제 업로드 화면의 제한을 기준으로 판단한다.

| 상황 | 선택 |
|---|---|
| 월 1~2회, 문서 2개, 코드 일부 | 무료 계정으로 샘플 1회 검증 |
| 릴리스마다 여러 문서와 긴 코드 비교 | 한도·맥락·프로젝트 재사용성을 확인한 뒤 유료 검토 |
| 고객 코드·비공개 키·취약점 정보 포함 | 개인 계정 업로드 금지, 회사 승인 환경 사용 |

체크리스트의 완료 조건은 “AI가 맞다고 했다”가 아니다. 원문 근거가 모든 변경 항목에 붙어 있고, 영향 파일을 검색했으며, 테스트·롤백 방법이 기록되어야 한다. 문서가 스캔 PDF거나 새 버전과 구버전의 범위가 다르면 분석을 중단하고 텍스트 문서와 공식 예제를 따로 준비한다.

핵심은 모델의 코딩 실력을 겨루는 데 있지 않다. 무료로 작은 변경을 통과시켜 보고, 반복 업로드와 팀 보안이 실제 병목일 때만 유료 플랜을 검토하면 된다. 최종 병합과 배포 판단은 개발자가 맡아야 한다.
